1. 产品定义
光衡是一套运行在 Home Assistant 生态上的家庭能源 Autonomous Energy Agent，由 Flutter App、Home 
Assistant、Hermes Agent、Energy Optimizer、Safety Policy、Anker SOLIX 官方集成和 ESP32-S3 光衡终端组成。
核心问题
不是“现在电池还有多少”，而是：为了接下来会发生的天气、电价、负载和光伏变化，现在是否值得调整储能计划？如果
值得，系统应该主动提出什么方案，并在用户批准后安全执行？

价值验证 Baseline vs Optimized 节省、自用率、备电结果
1.2 产品原则
 Agent 主动，不等用户发指令。
 LLM 负责理解上下文和编排，Optimizer 负责确定性数值。
 默认 Confirm Mode：真实设备执行前必须获得用户批准。
 批准的是一个锁定的 Plan ID；如果关键数据变化导致方案失效，必须重新计算并重新确认。
 执行不是终点，必须回读状态并验证。

2. 赛题对齐
赛题要求设计并实现一个可在 Home Assistant 中运行的家庭能源大脑，并结合 Anker SOLIX 官方插件的实时功率、电池
状态、控制写入能力，完成预测、决策、执行与解释，形成可感知、可演示、可验证的能源价值闭环。V3.0 将每个要求
映射为明确模块。

停电备电 Reserve SOC / BACKUP Policy 提高最低 SOC
预测 PV / Load / Price Forecast 24h Plan
决策 Hermes Opportunity Detection 主动生成 Proposal
执行 HA → SOLIX Adapter 写入 / Mock 同 Schema
解释 Decision Evidence + Explain Engine 通知 / 详情页
可感知 Push + 光衡终端 Aura / Lift 用户不主动打开 App 也能知晓
可验证 Execution Verification + Baseline 状态回读 + 报表
V3.0 的核心差异
不是“用户打开 App 后让系统优化”，而是“系统先发现值得优化的事情，主动把一个可解释、可验证的方案交给用户确
认”。
2.1 目标用户
拥有或计划使用家庭光伏 / 储能、处于峰谷或动态电价环境，希望降低电费、提高光伏自用率与备电安全，但不希望每
天盯着数据并手动调整计划的家庭用户。
2.2 非目标
 不做强化学习、复杂用户习惯学习、多家庭权限、多 Agent 社会。
 不做 EV、复杂全屋设备联动。
 不重写 SOLIX 底层协议。
 不让 LLM 直接自由生成低层充放电命令。
 不在 24h MVP 内实现 NFC、LRA 震动。

3. V3.0 主体验：Autonomous Energy Agent + Human Approval
Home Assistant / SOLIX / Weather / Tariff 数据进入
↓ Hermes 持续观察并识别机会 / 风险
↓ 判断是否值得 Replan
↓ 调用 Energy Optimizer
↓ 生成 Decision Proposal（旧方案 vs 新方案）
↓ App Push / 光衡终端主动提醒
↓ 用户：允许执行 / 暂不执行 / 查看原因
↓ Safety Policy 二次校验
↓ Home Assistant → SOLIX 执行
↓ 回读真实状态并 Verify
↓ App / 终端反馈结果，报表累计价值
3.1 为什么需要用户确认
能源设备属于真实物理执行系统。V3.0 选择“Agent 主动、用户确认”的中间态：智能性体现在系统主动发现与提出方
案；安全性体现在用户对重大真实写入保留最终批准权。
模式 行为 V3.0
Observe 只观察和解释，不执行 可作为 Debug
Confirm Agent 自主判断，用户批准后执行 MVP 默认
Autopilot 白名单内自动执行，重大动作仍确认 P2 / 后续
3.2 什么情况下生成提案
 未来低价窗口即将出现，且提前充电具备明确收益。
 未来高峰电价即将出现，需要准备放电。
 天气从晴转阴 / 光伏预测显著下降，当前计划可能不足。
 天气转好 / PV 预测上升，应减少夜间充电给光伏留空间。
 实际负载显著偏离预测，需要重新规划。
 SOC 低于计划轨迹或执行未达到目标。
 BACKUP 策略或异常事件要求提高 Reserve SOC。

4. Hermes Agent 在光衡中的职责
定位
Hermes 是主动观察与工具编排层，不是数值优化器。它决定“是否需要做点什么”和“应该调用哪些工具”，Optimizer 决
定“具体怎么充、怎么放”。
4.1 部署方式
组件 部署 说明
Hermes Agent 租用 Linux / VPS，先测试 1 个月 常驻运行；不放在 ESP32-S3
Home Assistant 本地 / 树莓派 / 测试环境 状态与执行总线
Optimizer API 同服务器或独立 FastAPI 确定性计算
Flutter App Android + iOS 批准、解释、报表、设备管理
ESP32-S3 终端 Wi-Fi 连接后端 / HA Ambient 感知与快速批准入口
4.2 Hermes 工具边界
能力 是否允许 说明
读取 HA Entity 允许 SOC、功率、状态、时间戳
读取天气 / 电价 允许 作为上下文
调用 Optimizer 允许 输入标准化上下文，获得数值计划
生成解释 允许 根据真实证据解释计划变化
直接自由生成“1374W”并写设备 禁止 必须由 Optimizer 输出
在无批准情况下调用高风险写操作 禁止 MVP 默认 Confirm Mode
批准后调用白名单 HA Service 允许 仍需 Safety Policy 校验
4.3 Home Assistant 连接能力
Hermes 官方 Home Assistant 集成支持通过 Gateway 订阅实时状态变化，并提供实体查询、服务发现和服务调用能
力。V3.0 只启用与能源相关的白名单 Entity / Service，并通过单独的 Executor 封装真实写入。
安全原则
即使 Hermes 具备 ha_call_service，也不让它直接对 SOLIX 裸写。所有能源写操作统一走 apply_energy_plan(plan_id) / 
set_reserve_soc(...) 等受控接口。

5.2 Forecast MVP
 PV Forecast：天气 × 时段 × 基础光伏曲线；Hackathon 不上复杂 ML。
 Load Forecast：最近 7 天同小时平均 / 中位数；无历史时使用家庭模板。
 Price Forecast：直接使用电价时段或 Mock Scenario。
5.3 Optimizer MVP
时间片 30 分钟或 1 小时，覆盖未来 24h；输入电池容量、初始 SOC、充放电功率限制、效率、最低 / 最高 SOC、PV / 
Load / Price 以及策略约束。
策略 目标函数倾向
SAVE 购电成本最低，较积极利用低谷与高峰价差
AUTO 成本 + 光伏自用 + Reserve 综合平衡
BACKUP Reserve SOC 权重最高，减少套利放电
5.4 Hermes  与Optimizer 的分工示例
Hermes：天气变化显著 → 当前计划可能不足 → 需要 Replan
Optimizer：Target SOC 45% → 75%，00:30-03:00 充电 1.2kW
Hermes：把变化解释成“为什么、影响什么、值不值得”
App：向用户提交可批准 Proposal

6. Decision Proposal：执行前的核心数据对象
V3.0 新增 Decision Proposal，所有真实写入必须绑定 Proposal ID。用户批准的是一个具体、可追踪、可过期的计划，
而不是一个模糊的“允许 AI 控制”。
字段 示例 用途
proposal_id GH-20260917-001 唯一追踪
trigger weather_replan 为什么触发
created_at 2026-09-17 12:30 时间戳
old_target_soc 45% 旧计划
new_target_soc 75% 新计划
window 00:30-03:00 执行窗口
charge_power 1.2 kW Optimizer 输出
reserve_soc 50% 硬约束
evidence[] PV -37%、低价窗口、高峰价 解释证据
estimated_impact 减少高峰购电 价值描述
expires_at 计划窗口前 防止旧方案误执行
approval_state pending/approved/rejected/expired 状态机
6.1 Approval 状态机
PENDING → 用户查看
→ APPROVED → Safety Recheck → EXECUTING → VERIFIED
→ REJECTED：记录原因，不执行
→ EXPIRED：关键数据变化或超时 → 重新 Replan
6.2 批准后再次校验
 SOC 是否仍在预期范围。
 电价 / 天气 / 负载是否发生重大变化。
 设备是否在线。
 目标功率是否仍在能力范围。
 Proposal 是否未过期。
 Plan ID 是否与用户批准的一致。

7. Safety Policy 与真实设备控制
硬规则
任何 Agent 判断都不能绕过 Safety Policy。出现数据缺失、时间戳过旧、实体不可写、设备离线、功率越界或 SOC 越界
时，系统必须拒绝真实写入。
检查项 策略
SOC 下限 / 上限 严格限制在配置范围
最大充 / 放电功率 不超过设备能力与当前接口上限
Reserve SOC BACKUP / 用户策略优先
数据新鲜度 关键 Entity 超时则禁止写入
服务白名单 只允许已验证的 HA Service / Script
Proposal ID 必须存在且已批准
方案漂移 输入变化超阈值则使 Proposal 失效
执行失败 停止连续写入，回退安全状态并通知
7.1 SOLIX Adapter
上层不依赖具体 Entity 名称。开工第一小时读取官方插件实际暴露的 Entity / Service，并冻结映射表；上层统一调用适
配器能力。
apply_energy_plan(plan_id)
set_reserve_soc(value)
set_energy_mode(mode)
get_energy_state()
verify_execution(plan_id)
7.2 执行验证
执行后不是“命令返回 200 就算成功”，而是等待短时间后重新读取 battery_power / SOC / writable state，判断设备
是否真实进入目标状态。

24. 最终产品叙事
比赛现场不要把光衡描述成“AI + HA + ESP32 的组合”，而要描述成一个主动工作的家庭能源 Autopilot。
最终叙事
Hermes 负责持续观察家庭能源环境、发现什么时候值得重新规划；Optimizer 负责把天气、电价、光伏和负载变成确定性的 
24 小时计划；用户只在真实设备将被改变前收到一个清楚的决策提案；批准后由 Safety Policy、Home Assistant 和 SOLIX 
完成安全执行，并通过状态回读验证结果。光衡 App 与光衡终端负责让整个过程随时可见、可理解、可干预。
24.1  评委3-5 分 点钟记忆
 Agent 不是等人输入，而是主动发现“现在该做什么”。
 天气变化触发 Replan：45% → 75%。
 真实执行前生成 Proposal，由用户一键批准。
 LLM 不直接算功率，Optimizer + Safety 承担数值和安全边界。
 SOLIX 执行后状态回读，明确显示 Verified。
 Energy Clock + Lift-to-Explain 让后台决策变成可感知实体体验。
 Baseline vs Optimized 证明价值，而不是只展示数据。
24.2 一句话收尾
光衡不是让用户更会管理电池，而是让系统先替用户把能源问题想清楚，在真正需要改变设备
时，只把一个值得批准的决定交给用户。
