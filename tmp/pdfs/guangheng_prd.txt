1. 产品定义
光衡是一套运行在 Home Assistant 生态上的家庭能源智能调度系统，由 Flutter App、Home Assistant、
Energy Brain、MCP 能力层、Energy Optimizer、Anker SOLIX 官方集成和 ESP32-S3 光衡终端组成。
核心不是“看电量”
系统要回答：现在这一度电应该存着、用掉，还是为未来留着？随后将可验证的计划写入 SOLIX，并让用
户在 App 和光衡终端上理解“为什么这样做、未来会怎样、这样做值不值得”。
1.1 核心闭环
阶段 输入 / 动作 输出
感知 SOLIX SOC / 功率、电价、天气、家庭负载 当前能源上下文
预测 未来电价、光伏条件、基础负载趋势 未来 24h 约束
决策 Energy Brain 选择优化目标 SAVE / AUTO / BACKUP
优化 Optimizer 计算确定性充放电计划 时间、功率、Reserve SOC
执行 Home Assistant -> SOLIX 官方集成 设备状态改变
解释 App + 光衡终端展示证据与变化 为什么这样做 / 预计节省多少
感知增强
GuangHeng Sense 将变化转为光、触觉、
姿态交互
用户不打开 App 也能感知重要事件
验证 Baseline vs Optimized 成本、自用率、备电结果
1.2 24 小时 Hackathon 核心目标
 App 能在 3 秒内表达当前家庭能源状态。
 系统能生成并解释未来 24 小时策略。
 策略通过 Home Assistant 进入 SOLIX 控制链路，或使用同 Schema 的 Mock / Replay 证明闭环。
 App 和光衡终端共享同一 energy_mode 与策略结果。
 光衡终端不复制 App，而是用 GuangHeng Sense 增强用户对能源决策的感知。
 用同场景 Baseline vs Optimized 证明策略价值。

2. 赛题理解与用户问题
家庭储能面对的是一个未来决策问题：天气、电价、光伏与家庭负载持续变化，固定时段规则无法长期保持最
优。光衡的价值不止是“自动执行”，而是让系统能够根据未来变化提前行动，并把这种行动解释清楚。
核心矛盾
传统自动化回答“到点做什么”；光衡回答“为了即将发生的事情，现在应该做什么”。
2.1 目标用户
已经拥有或计划使用阳台光伏 / 家庭储能，并处于峰谷或动态电价环境，希望降低电费、提高光伏自用率与备
电安全，但不愿每天手动调整充放电策略的家庭用户。
2.2 四个关键痛点
痛点 表现 光衡回应
数据有了，决策仍靠人
SOC、PV、Load 可见，但用户仍需自己判
断何时充、何时放
Optimizer 生成可执行 24h 计划
固定规则无法适应未来变化
晴转阴、连续阴雨、动态电价会改变最佳
策略
Weather / Tariff Context 触发 Replan
自动化缺乏解释 用户不知道为什么突然充电 / 放电 App 与终端给出证据和前后变化
后台决策缺乏感知 只有主动打开 App 才能发现策略变化
GuangHeng Sense 用光、触觉和抬起交互
主动呈现重要变化
2.3 为什么还需要硬件
App 与硬件不是竞争关系
App 用来深度管理能源；光衡终端负责“抬眼即见、变化可感、随手可控”。硬件位于手机之前的感知
层：先让用户意识到值得关注的变化，需要深入理解时再进入 App。
光衡 App 光衡终端
完整能源 Dashboard Ambient 状态感知
详细策略证据与 24h 计划 Energy Clock 快速看未来

4.3 App 权限管理原则
 最小权限：没有真实功能需求就不申请权限。
 通知：用于策略重算、异常、Future Alert；用户可随时关闭。
 本地网络：仅在手机需要发现 / 连接 Home Assistant 或光衡终端时启用。
 蓝牙：仅用于终端首次配网 / 绑定时的可选路径；若 P0 只走 Wi-Fi，则不申请。
 定位：不作为产品核心权限；仅在特定系统版本的蓝牙 / 网络发现确实要求时说明原因并请求。
 相机：只有引入二维码配网时才请求。
 权限页职责：显示系统授权状态、跳转系统设置，不伪造权限状态。

5. Energy Brain、MCP 与 Optimizer
设计原则
LLM 不直接计算“放 763W”或自由构造低层指令。AI / MCP 负责理解上下文、选择目标与解释；
Optimizer 负责确定性数值调度；Safety Policy 负责硬约束。
5.1 MCP 能力层
能力 职责 Hackathon
Home Assistant Context / MCP
读取 SOC、功率、实体状态；调用受控能
力
P0
Weather Context 天气、光伏条件、恶劣天气信号 P0（API 或固定场景）
Tariff Context 当前 / 未来电价时段 P0
Energy Optimizer Tool 生成 24h 充放电计划 P0
GuangHeng Intent Context SAVE / AUTO / BACKUP 用户意图 P0
Calendar / Household Context 家庭事件 P2，不进入 24h 核心
5.2 策略算法 MVP
 第一版使用时间片离散 + 规则约束 / 简单优化，不追求强化学习。
 输入：初始 SOC、容量、最大充放电功率、效率、最低 / 最高 SOC。
 时间片：30 分钟或 1 小时，共 24-48 个 slot。
 成本：GridImport(t) × Price(t)。
 约束：SOC 边界、功率上限、BACKUP 最低 SOC。
 AUTO：成本 + 光伏自用 + 备用惩罚；SAVE：成本权重最高；BACKUP：备用 SOC 权重最高。
5.3 不做“使用习惯学习”
 有历史数据：最近 7 天同一小时平均 / 中位数。
 无历史数据：预设家庭负载模板 + 当前负载修正。
 UI 只写“预计晚间负载上升”，不写“AI 已学习你的习惯”。
5.4 Safety Policy
 SOC 不低于策略最低值。

9.6 Energy Handoff

10.1 主 Demo - 动态电价

10.2 次 Demo - 天气变化触发 Replan
9. 初始天气预测为晴天，夜间目标 SOC 设为 45%，给次日光伏留空间。

15. 开发基线结论
Go / No-Go：GO
V2.0 已把产品重新收敛为一条清晰主线：AI / MCP 理解上下文，Optimizer 生成确定性计划，Home

15.1 最终产品叙事
不要把项目描述成“AI + Home Assistant + ESP32”。比赛现场应讲成：
光衡的系统分工
AI 负责理解未来；Optimizer 负责做可验证的决策；SOLIX 负责执行；光衡 App 负责深度管理；光衡终端
负责把后台决策变成人能看到、感觉到、理解并快速干预的体验。
